## 1. Overview

The ForgeOS dashboard replaces the current static HTML dashboard generated by `todo_visual.py`. The new dashboard provides a real-time, interactive web interface for Human Operators and System Administrators to monitor and manage the multi-agent ticket pipeline.

### Target Technology

| Aspect | Choice | Rationale |
|--------|--------|-----------|
| Framework | Vanilla HTML + CSS + JavaScript | No build step. Single-file deployment. Per CAP-05 architecture decision. |
| Graphs | D3.js | Force-directed dependency graph. Proven for DAG visualization. |
| Real-time | Server-Sent Events (SSE) | Unidirectional push from server. Simpler than WebSocket for read-heavy dashboard. Auto-reconnect built into browser `EventSource` API. |
| Styling | CSS custom properties | Theme-able. No preprocessor dependency. |

### Personas Served

| Persona | Primary Views | Interaction Mode |
|---------|---------------|------------------|
| Human Operator | Pipeline Overview, Ticket Detail, Dependency Graph | Daily monitoring, filtering, drill-down |
| System Administrator | Claim Monitor, Agent Status, all operator views | Escalation response, health monitoring, configuration |

### Pain Points Addressed

This dashboard directly addresses the following pain points documented in the [User Personas](user-personas.md) reference:

| Pain Point | Solution |
|-----------|----------|
| No real-time updates (rank 2) | SSE push from `pg_notify` with sub-second latency |
| No search or filtering (rank 4) | Faceted filters on stage, priority, assignee, tag, date range |
| Scattered state (rank 5) | Unified dashboard drawing from a single PostgreSQL database |
| No visibility into agent status (rank 6) | Dedicated Agent Status and Claim Monitor views |

## 2. Design Principles

1. **Information density over decoration.** Show maximum useful data per screen. Avoid whitespace-heavy layouts that require scrolling. Operators monitor dozens of tickets simultaneously.
2. **Zero-click awareness.** The default view (Pipeline Overview) must show pipeline health without any interaction. Operators glance at it between tasks.
3. **Progressive disclosure.** Summary first, detail on click. Pipeline Overview → Stage column → Ticket card → Ticket Detail panel.
4. **Keyboard-first navigation.** All actions available via keyboard shortcuts. Mouse is optional. Operators work in terminal-heavy workflows.
5. **Real-time by default.** All views update live via SSE. No refresh button. No polling toggle. Data is always current.
6. **Fail-safe visibility.** When the SSE connection drops, the dashboard shows a visible "Disconnected" banner with reconnection countdown. Stale data is marked as stale.

### 3.3 Ticket Card

Each ticket card in a column shows:

| Element | Content | Format |
|---------|---------|--------|
| Ticket ID | `FORGEOS-PM004` | Monospace, clickable link to Ticket Detail |
| Title | First 40 characters + ellipsis | Regular text, full title on hover tooltip |
| Priority | critical / high / medium / low | Color-coded badge: red / orange / blue / gray |
| Assignee | Agent name or "Unclaimed" | Text below title |
| Time in stage | Duration since entering current stage | `2h 15m` format, turns red after configurable threshold |
| Rework indicator | Rework count if > 0 | Orange badge: `R1`, `R2`, `R3` |

### 3.4 Column Header

Each stage column header displays:

| Element | Content |
|---------|---------|
| Stage name | Full SDLC stage name |
| Ticket count | Number of tickets currently in this stage |
| Average time-in-stage | Mean duration of all tickets in the column |

### 3.5 Drag-and-Drop Consideration

**Decision: Do NOT implement drag-and-drop for stage transitions.**

Rationale: Stage transitions are governed by the SDLC engine and two-commit protocol. Manual drag-and-drop would bypass validation guards, skip required stages, and violate the ticket-system rules. Operators use `tickets.py --advance` or MCP tools for controlled transitions.

Exception: The "Release" action on expired claims is triggered via a button, not drag-and-drop.

### 3.6 Filtering Requirements

| Filter | Type | Behavior |
|--------|------|----------|
| Stage | Multi-select dropdown | Show only selected stages. Default: all stages visible. |
| Priority | Multi-select dropdown | Filter by critical, high, medium, low. |
| Assignee | Text autocomplete | Filter by agent name or operator name. |
| Tag | Multi-select dropdown | Filter by ticket tags (e.g., `phase1`, `backend`). |
| Type | Multi-select dropdown | Filter by ticket type: backend, frontend, fullstack, infra, security, docs, research, architecture. |
| Date range | Date picker (from–to) | Filter by `created_at` date range. |
| Search | Free-text input | Search ticket ID, title, and description. Debounced at 300ms. |

**Filter behavior:**
- Filters combine with AND logic (intersection).
- Active filters persist in the URL query string for bookmarking and sharing.
- A "Clear all filters" button resets to default.
- Filter counts update in real time as tickets change stage.

## 4. View 2: Ticket Detail

### 4.1 Purpose

Show complete information for a single ticket. Opens as a slide-over panel from the Pipeline Overview or as a standalone URL (`/tickets/{ticket-id}`).

**User story reference:** HO-01 (drill-down on stage click), HO-03 (manual intervention actions).

### 4.2 Information Sections

#### 4.2.1 Header

| Field | Content |
|-------|---------|
| Ticket ID | `FORGEOS-PM004` (copyable) |
| Title | Full title text |
| Priority badge | Color-coded priority |
| Stage badge | Current SDLC stage |
| Type badge | Ticket type (backend, frontend, etc.) |

#### 4.2.2 Metadata Panel

| Field | Content |
|-------|---------|
| Created at | ISO 8601 timestamp with relative time (`2 days ago`) |
| Created by | Agent or operator that created the ticket |
| Claimed by | Current claimer or "Unclaimed" |
| Machine ID | Machine holding the current claim |
| Operator | Human operator associated with the claim |
| Lease expiry | Countdown timer. Red when < 5 minutes remaining. |
| Rework count | `0/3` with progress indicator |
| Source task file | Link to the L3 task markdown file |

#### 4.2.3 Acceptance Criteria

Display each acceptance criterion as a checklist item:

| State | Display |
|-------|---------|
| Not started | Empty checkbox, gray text |
| In progress | Half-filled checkbox, blue text |
| Met | Green checkmark, green text |
| Failed | Red X, red text with rejection reason |

Note: Acceptance criteria status is derived from agent output summaries and QA/Validator results. The dashboard does not allow manual checkbox toggling.

#### 4.2.4 File Paths

List of files in the ticket's `file_paths` array. Each path is a clickable link that opens the file in the repository browser (GitHub).

#### 4.2.5 Dependencies

| Direction | Display |
|-----------|---------|
| Depends on (upstream) | List of ticket IDs with their current stage. Green if DONE, yellow if in progress, red if BLOCKED. |
| Blocks (downstream) | List of ticket IDs that depend on this ticket. |

#### 4.2.6 History Timeline

Chronological event log showing all ticket lifecycle events:

| Event Type | Display |
|------------|---------|
| CREATED | Gray dot, creation details |
| MOVED_TO_READY | Green dot, dependency resolution note |
| CLAIMED | Blue dot, agent name + machine ID |
| STAGE_ADVANCED | Green dot, from-stage → to-stage |
| REJECTED | Red dot, rejection reason + rejecting agent |
| REWORK | Orange dot, rework count + reason |
| ESCALATED | Red dot, escalation details |
| COMPLETED | Green dot, completion summary |
| LEASE_EXPIRED | Yellow dot, expired claim details |
| RELEASED | Gray dot, manual release details |

Each event shows timestamp (absolute + relative), acting agent, and machine ID.

#### 4.2.7 Agent Output

Render the agent's latest summary markdown (from `.github/agent-output/{AgentName}/{ticket-id}.md`) inline. Show the most recent summary for the current stage, with a collapsible history of previous stage summaries.

### 4.3 Actions

| Action | Visibility | Behavior |
|--------|-----------|----------|
| Release claim | Shown when claim is expired | Calls `tickets.release` MCP tool. Returns ticket to current stage unclaimed. |
| Rework | Shown when ticket is in post-implementation stages | Prompts for rework reason. Calls `tickets.reject` MCP tool. |
| Escalate | Shown when rework count = 3 | Moves ticket to ESCALATED. Disables further rework. |
| Copy ticket ID | Always shown | Copies ticket ID to clipboard. |
| Open in GitHub | Always shown (if source path exists) | Opens source task file in GitHub. |

## 5. View 3: Dependency Graph

### 5.1 Purpose

Visualize the ticket dependency DAG (Directed Acyclic Graph) as an interactive force-directed graph using D3.js.

**User story reference:** HO-06 (Dependency Graph Visualization) — Could priority.

### 5.2 Graph Elements

| Element | Visual | Encoding |
|---------|--------|----------|
| Ticket node | Circle | Size proportional to number of dependents. Color = stage (same palette as Pipeline Overview columns). |
| Dependency edge | Directed arrow | From dependency → dependent ticket. Solid line for resolved, dashed for unresolved. |
| Critical path | Highlighted edge | Bold red edges on the longest blocking chain. |
| Cluster | Background region | Tickets grouped by type or phase, with translucent background. |

### 5.3 Node Details

Hovering on a ticket node shows a tooltip with:

| Field | Content |
|-------|---------|
| Ticket ID | Full ID |
| Title | Full title |
| Stage | Current SDLC stage |
| Priority | Priority level |
| Assignee | Current claimer or "Unclaimed" |
| Blocking | Number of tickets blocked by this one |
| Blocked by | Number of unresolved dependencies |

Clicking a node navigates to the Ticket Detail view.

### 5.4 Interactions

| Interaction | Behavior |
|------------|----------|
| Zoom | Mouse wheel or pinch gesture. Range: 25%–400%. |
| Pan | Click and drag on background. |
| Node drag | Click and drag a node to reposition. Graph relaxes around new position. |
| Filter | Same filter controls as Pipeline Overview. Filtered-out nodes fade to 10% opacity. |
| Highlight path | Click a node to highlight all upstream and downstream dependencies. Other nodes fade. |
| Reset | Double-click background to reset zoom, pan, and highlights. |

### 5.5 Layout Algorithm

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Layout engine | D3 force-directed | Natural clustering of related tickets. |
| Link distance | 100px base, scaled by dependency depth | Keep close dependencies visible together. |
| Charge strength | -300 | Prevent node overlap while maintaining density. |
| Collision radius | 30px | Minimum spacing between node centers. |
| Centering force | Enabled | Keep graph centered in viewport. |

### 5.6 Performance Constraints

| Ticket Count | Behavior |
|-------------|----------|
| ≤ 100 | Full graph rendered. All animations enabled. |
| 101 – 500 | Disable animation transitions. Static layout after initial computation. |
| 501 – 1000 | Show warning: "Large graph. Consider filtering." Disable force simulation after 3 seconds. |
| > 1000 | Do not render full graph. Show filtered subgraph (e.g., tickets matching current filters only). |

## 6. View 4: Claim Monitor

### 6.1 Purpose

Display all active claims across every stage, showing which agent holds which ticket, on which machine, with lease countdown timers.

**User story reference:** HO-02 (Monitor Agent Claims) — Must priority.

### 6.2 Layout

A sortable, filterable table:

| Column | Content | Sortable | Default Sort |
|--------|---------|----------|--------------|
| Ticket ID | Clickable link to Ticket Detail | Yes | — |
| Title | First 50 characters | Yes | — |
| Stage | Current SDLC stage | Yes | — |
| Agent | Claiming agent name | Yes | — |
| Machine | Machine ID (`hostname`) | Yes | — |
| Operator | Human operator name | Yes | — |
| Claimed at | Timestamp of claim event | Yes | Descending (newest first) |
| Lease remaining | Countdown timer (mm:ss) | Yes | Ascending (expiring soonest first) |
| Status | Active / Expiring / Expired | Yes | — |

### 6.3 Status Indicators

| Status | Condition | Visual |
|--------|-----------|--------|
| Active | Lease remaining > 10 minutes | Green dot |
| Expiring | Lease remaining ≤ 10 minutes and > 0 | Yellow dot, pulsing animation |
| Expired | Lease remaining ≤ 0 | Red dot, "Release" button appears |

### 6.4 Actions

| Action | Trigger | Behavior |
|--------|---------|----------|
| Release | Click "Release" on expired claim | Calls `tickets.release` MCP tool. Row disappears from table. Ticket returns to stage unclaimed. |
| Release All Expired | Button above table | Batch-releases all expired claims. Confirmation dialog required. |
| Refresh | Manual refresh button (in addition to SSE) | Forces a full data reload from the server. |

### 6.5 Machine Grouping

Toggle between flat table view and grouped view:

- **Flat view:** All claims in one table (default).
- **Grouped by machine:** Claims grouped under machine ID headers. Shows machine claim count, total active time, and last activity timestamp.
- **Grouped by agent:** Claims grouped by agent type. Shows agent workload distribution.

## 8. Interaction Patterns

### 8.1 Navigation

| Pattern | Implementation |
|---------|---------------|
| Tab-based main navigation | Tabs: Pipeline \| Graph \| Claims \| Agents |
| URL routing | Hash-based routing (`#/pipeline`, `#/graph`, `#/claims`, `#/agents`). No server-side routing since the dashboard is a static file. |
| Breadcrumbs | Shown in Ticket Detail: Pipeline > Stage > Ticket ID |
| Keyboard shortcuts | `1`–`4` for tab switching, `/` for search focus, `Esc` to close panels, `?` for shortcut help |

### 8.2 Filtering

| Pattern | Behavior |
|---------|----------|
| Filter bar | Persistent horizontal bar below main tabs. Visible on all views. |
| Filter persistence | Active filters apply across all views. Changing tabs preserves filters. |
| URL sync | Filter state encoded in URL query parameters for bookmarking. |
| Filter presets | Saved filter combinations: "My tickets" (filter by operator), "Critical only", "Blocked tickets". |
| Clear filters | Single "Clear all" button resets all filters. |

### 8.3 Sorting

| Pattern | Behavior |
|---------|----------|
| Column header click | Single click sorts ascending, second click descending, third click removes sort. |
| Multi-column sort | Hold Shift + click for secondary sort. |
| Sort indicator | Arrow icon in column header (▲ ascending, ▼ descending). |
| Default sort | Views have sensible defaults: Pipeline by stage order, Claims by lease expiry. |

### 8.4 Search

| Pattern | Behavior |
|---------|----------|
| Global search | Search bar in the top navigation. Searches ticket ID, title, description, and tags. |
| Debounce | 300ms debounce to avoid excessive queries during typing. |
| Results display | Inline dropdown showing top 10 matches. Click to navigate to Ticket Detail. |
| Empty state | "No tickets match your search" with suggestion to adjust filters. |

### 8.5 Drill-Down

| Level | View | Trigger |
|-------|------|---------|
| L0 | Pipeline Overview | Default landing page |
| L1 | Stage column detail | Click a stage column header |
| L2 | Ticket card summary | Ticket card visible in column |
| L3 | Ticket Detail panel | Click a ticket card |
| L4 | Agent output/history | Expand sections within Ticket Detail |

## 9. Real-Time Update Requirements

### 9.1 Transport

| Aspect | Requirement |
|--------|-------------|
| Protocol | Server-Sent Events (SSE) via `EventSource` API |
| Endpoint | `GET /events` with `Accept: text/event-stream` header |
| Authentication | Bearer token passed as query parameter (`?token=...`) since `EventSource` does not support custom headers natively |
| Reconnection | Browser `EventSource` auto-reconnects. Server sends `retry: 5000` to set 5-second reconnect interval. |

### 9.2 Event Types

| Event | Payload | Dashboard Update |
|-------|---------|-----------------|
| `ticket_created` | Full ticket JSON | Add card to READY column |
| `ticket_claimed` | `{ticket_id, agent, machine_id, lease_expiry}` | Update card assignee, add to Claims table |
| `stage_advanced` | `{ticket_id, from_stage, to_stage}` | Move card between columns with animation |
| `ticket_rejected` | `{ticket_id, reason, rejecting_agent}` | Flash card red, update rework badge |
| `ticket_completed` | `{ticket_id, summary}` | Move card to DONE, update counters |
| `lease_expired` | `{ticket_id, agent}` | Mark claim as expired in Claims table |
| `lease_extended` | `{ticket_id, new_expiry}` | Reset countdown timer in Claims table |
| `ticket_escalated` | `{ticket_id, rework_count}` | Move card to ESCALATED section, flash red |
| `agent_connected` | `{agent_name, machine_id, session_id}` | Update Agent Status view |
| `agent_disconnected` | `{agent_name, session_id}` | Update Agent Status view |
| `health_update` | `{db_status, pool_stats, uptime}` | Update System Health panel |

### 9.3 Optimistic UI Updates

| Scenario | Behavior |
|----------|----------|
| Operator releases a claim | Immediately remove from Claims table. If server rejects, re-add with error toast. |
| Operator triggers rework | Immediately show rework badge on card. If server rejects, revert with error toast. |

### 9.4 Connection Handling

| State | Visual Indicator | Behavior |
|-------|-----------------|----------|
| Connected | Green dot in header: "Live" | Normal operation. Events update UI in real time. |
| Reconnecting | Yellow dot in header: "Reconnecting..." with countdown | Browser auto-reconnects at 5-second intervals. Data may be stale. |
| Disconnected (> 30 seconds) | Red banner across top: "Connection lost. Data may be stale. [Retry]" | Manual retry button. All timestamps marked as "last updated X seconds ago". |
| Reconnected after gap | Green dot restored. Full data refresh triggered. | Fetch full state from API to reconcile any missed events during disconnection. |

### 9.5 Event Delivery Guarantees

| Consideration | Approach |
|--------------|----------|
| Missed events during reconnect | On reconnect, client sends `Last-Event-ID` header. Server replays missed events from the `events` table. |
| Event ordering | Events include a monotonically increasing sequence number. Client discards out-of-order events. |
| Duplicate events | Client deduplicates by event ID. Applying the same event twice is idempotent (move card to same column = no-op). |

## 10. Multi-Machine Visibility

### 10.1 Purpose

ForgeOS supports multiple operators on multiple machines running agents concurrently. The dashboard must clearly show which machine holds which claim and identify potential conflicts.

### 10.2 Machine Identification

| Field | Source | Display |
|-------|--------|---------|
| Machine ID | `hostname` from claim metadata | Displayed in Claim Monitor and Ticket Detail |
| Operator | Human operator associated with the machine | Displayed alongside machine ID |
| IP address | Not stored (privacy). Machine identification is by hostname only. | — |

### 10.3 Machine Status Indicators

| Indicator | Meaning | Visual |
|-----------|---------|--------|
| Machine badge on ticket card | Shows which machine holds the claim | Small pill badge: `pop-os`, `dev-1`, etc. |
| Machine color coding | Each unique machine gets a consistent color | Auto-assigned from a palette of 8 distinguishable colors |
| Machine filter | Filter Claims and Pipeline views by machine | Dropdown in filter bar |

### 10.4 Conflict Indicators

| Conflict Type | Detection | Visual |
|--------------|-----------|--------|
| File path overlap | Two claimed tickets share entries in `file_paths` | Orange warning icon on both ticket cards. Tooltip shows conflicting files and the other ticket ID. |
| Same-machine multiple claims | One machine holds claims on > 3 tickets simultaneously | Yellow info badge on machine in Claims table. |
| Stale machine | Machine's most recent activity was > 1 hour ago but claims remain active | Gray badge on machine. All claims from that machine show "Possibly stale" warning. |

### 10.5 Multi-Machine Dashboard

The Agent Status view includes a machine summary panel:

| Column | Content |
|--------|---------|
| Machine hostname | Unique machine identifier |
| Active claims | Number of currently held claims |
| Last activity | Timestamp of most recent claim, advance, or heartbeat from this machine |
| Operator | Human operator name |
| Status | Active / Idle / Stale |

## 13. Accessibility Requirements

| Requirement | Standard | Implementation |
|-------------|----------|---------------|

| Keyboard navigation | All interactive elements reachable via Tab | `tabindex` attributes, visible focus indicators |

| Status announcements | SSE updates announced to screen readers | `aria-live` region for connection status and new events |

## 14. Glossary

| Term | Definition |
|------|-----------|
| **Claim** | An agent's lock on a ticket. Gives exclusive right to process that ticket's current SDLC stage. |
| **DAG** | Directed Acyclic Graph. The dependency structure of tickets where edges represent `depends_on` relationships. |
| **Lease** | Time-limited claim. Expires after a configurable duration (default 30 minutes). Must be extended via heartbeat. |
| **Optimistic UI** | UI update pattern where the interface updates immediately before server confirmation, rolling back on failure. |
| **Progressive disclosure** | Design pattern that reveals information gradually, starting with summaries and drilling into detail on demand. |
| **SDLC stage** | One of 11 lifecycle stages a ticket passes through: READY, ARCHITECT, RESEARCH, BACKEND, FRONTEND, QA, SECURITY, CI, DOCS, VALIDATION, DONE. |
| **SSE** | Server-Sent Events. W3C standard for server-to-client push over HTTP. The `EventSource` browser API handles reconnection automatically. |
| **Sparkline** | A small, inline chart showing a trend (e.g., events per minute over the last hour). |
| **Time in stage** | Duration since a ticket entered its current SDLC stage. Used to identify bottlenecks. |
